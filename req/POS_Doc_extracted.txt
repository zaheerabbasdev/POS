Chapter 5 – Executive Summary
The Mobile Shop Point of Sale (POS) System is a web-based business management solution designed for mobile phone retailers. The system aims to simplify and automate daily business operations such as inventory management, product sales, purchases, customer management, supplier management, repair services, warranty tracking, expenses, and reporting.
The software will provide a centralized platform that enables users to perform sales quickly, monitor stock accurately, generate invoices, and access business reports in real time. The system is designed with scalability in mind so that future versions can support Pharmacy POS and Mart POS businesses without major architectural changes.

Chapter 6 – Business Overview
Mobile shops handle various business activities including selling smartphones, accessories, repair services, SIM cards, and warranty claims. Many small and medium-sized businesses still rely on manual record keeping or basic software, resulting in inventory inaccuracies, delayed reporting, and inefficient business operations.
The proposed Mobile Shop POS System will replace manual processes with a centralized digital solution that improves operational efficiency, inventory accuracy, sales tracking, and customer service. The system will provide real-time business information and support informed decision-making.

Chapter 15 – Business Process Overview

Inventory Process
Supplier → Purchase Order → Product Received → Stock Updated → Available for Sale

Sales Process

Purchase Process
Supplier Selected → Purchase Created → Stock Received → Inventory Updated → Supplier Payment Recorded

Repair Process
Customer Device Received → Repair Ticket Created → Technician Assigned → Repair Completed → Customer Notified → Device Delivered

Warranty Process
Product Sold → Warranty Registered → Warranty Period Tracked → Claim Processed if Required

Reporting Process
Business Transactions → Database → Reports Generated → Business Analysis

Chapter 17 – Business Rules
Business rules define the policies and guidelines that the Mobile Shop POS System must follow during daily operations.
17.1 User Management Rules
Every user must have a unique username or email. 
Users can only access features based on their assigned role. 
Inactive users cannot log in. 
Passwords must be securely stored in encrypted form. 
User activities should be recorded for auditing purposes. 

17.2 Product Rules
Every product must belong to a category. 
Every product must have a unique SKU. 
Mobile phones should be tracked using IMEI numbers. 
Accessories should be managed by quantity. 
Products can be marked as Active or Inactive. 
Products cannot be sold if they are out of stock. 

17.3 Inventory Rules
Stock increases after a successful purchase. 
Stock decreases after a successful sale. 
Stock adjustments must be recorded with a reason. 
Inventory history should be maintained. 
Low stock alerts should be generated automatically. 

17.4 Sales Rules
Each sale must generate a unique invoice number. 
Discounts must not exceed the configured limit. 
Completed sales cannot be edited directly. 
Sales returns must update inventory automatically. 
Payment status must be recorded for every sale. 

17.5 Purchase Rules
Every purchase must be linked to a supplier. 
Purchase invoices must have unique reference numbers. 
Stock should update only after purchase confirmation. 
Purchase returns should reduce inventory. 

17.6 Customer Rules
Customers can have multiple purchases. 
Customer purchase history should be maintained. 
Warranty information should be linked to customers. 
Customer balances should be updated automatically. 

17.7 Repair Rules
Every repair must have a unique repair ticket. 
Device IMEI should be recorded when available. 
Repair status must be updated throughout the process. 
Completed repairs should be stored in history. 

17.8 Warranty Rules
Warranty starts from the date of sale. 
Warranty period depends on the product. 
Expired warranties cannot be claimed. 
Warranty history should remain available.

Chapter 11 – Entity Relationships
Purpose
This chapter defines how the database tables relate to each other. Proper relationships ensure data integrity, reduce redundancy, and support efficient queries.

Authentication Relationships
Users ↔ Roles
One user can have one or more roles. 
One role can be assigned to many users. 
Relationship: Many-to-Many
Junction Table:
user_roles 

Roles ↔ Permissions
One role contains multiple permissions. 
One permission can belong to multiple roles. 
Relationship: Many-to-Many
Junction Table:
role_permissions 

Employee Relationships
Employee → User
One employee may have one system user account. 
A user account belongs to one employee. 
Relationship: One-to-One

Product Relationships
Brand → Product Model
One brand has multiple models. 
One model belongs to one brand. 
Relationship: One-to-Many
Example:
Samsung
Galaxy S24 
Galaxy S25 
Galaxy A56 

Category → Product
One category contains many products. 
One product belongs to one category. 
Relationship: One-to-Many
Example:

Chapter 14 – Database Constraints
The database shall enforce the following constraints.
Primary Key Constraint
Every table must have one primary key. 

Foreign Key Constraint
Related records must exist before insertion. 
Example:
A product cannot reference a category that does not exist.

Unique Constraint

Not Null Constraint
The following fields are mandatory where applicable:

Sale Date 
Purchase Price 
Selling Price 
Quantity 

Check Constraints
Examples:
Quantity ≥ 0 
Selling Price ≥ 0 
Purchase Price ≥ 0 
Discount ≥ 0 
Tax ≥ 0 

Default Values
Examples:
is_active = true 
created_at = current_timestamp 
updated_at = current_timestamp 
stock_quantity = 0 

Chapter 15 – Normalization Strategy
The database should be normalized to improve consistency and reduce duplication.
First Normal Form (1NF)
Store atomic values. 
Eliminate repeating groups. 

Second Normal Form (2NF)
Remove partial dependencies. 
Separate related information into dedicated tables. 

Third Normal Form (3NF)
Remove transitive dependencies. 
Store lookup values such as brands and categories separately.

Chapter 36 – Database Security
Security Requirements
Use SSL/TLS for database connections. 
Restrict database access by user roles. 
Store passwords using a secure hashing algorithm. 
Encrypt sensitive configuration values. 
Validate all database inputs. 
Protect against SQL Injection by using Prisma ORM and parameterized queries. 
Record database-related security events in audit logs.

Chapter 38 – Database Design Summary
The Mobile Shop POS database is designed using a modular relational structure that supports:
Authentication & Authorization 
Product Management 
IMEI Tracking 
Inventory Management 
Sales & Billing 
Purchases 
Customer Management 
Supplier Management 
Repair Management 
Warranty Management 
Expense Tracking 
Notifications 
Audit Logging 
System Configuration 
The design emphasizes:
Data integrity through foreign key relationships. 
Reduced redundancy through normalization. 
Scalability for future Pharmacy POS, Mart POS, and Multi-Branch support. 
Performance through appropriate indexing. 
Security using role-based access, encrypted credentials, and audit logging. 
Maintainability through consistent naming conventions and modular table organization.

Chapter 4 – Introduction
Purpose
This document describes the technical architecture and implementation approach for the Mobile Shop POS System. It provides a blueprint for developers to build, maintain, and scale the application.

Objectives
Define the overall architecture. 
Standardize the project structure. 
Describe communication between system components. 
Establish development standards. 
Ensure scalability and maintainability. 
Support future expansion for Pharmacy POS, Mart POS, and Multi-Branch operations.

Chapter 16 – Authentication Architecture
Authentication Method
The system shall use JWT (JSON Web Token) for authentication.

Login Flow
User Login
     │
▼
Validate Credentials
     │
▼
Generate JWT Access Token
     │
▼
Return Token
     │
▼
Client Stores Token
     │
▼
Authenticated API Requests

Authentication Process
User submits username/email and password. 
Backend validates credentials. 
Password is verified using bcrypt. 
JWT access token is generated. 
Token is returned to the client. 
Client includes the token in the Authorization header for subsequent requests. 
Protected endpoints validate the token before processing requests. 

JWT Payload
The token should contain:
User ID 
Username 
Employee ID 
Role IDs 
Issued Time 
Expiration Time

Chapter 22 – Database Transaction Strategy
Purpose
Ensure that related database operations succeed or fail together.

Transactions Required For
Sales creation 
Purchase creation 
Sales returns 
Purchase returns 
Stock adjustments 
Repair completion 
Warranty creation 

Example Workflow
Creating a sale should:
Create the sale record. 
Create sale items. 
Update inventory. 
Update IMEI status (if applicable). 
Create payment record (if payment received). 
Create warranty record (if applicable). 
Write an audit log. 
If any step fails, the entire transaction should be rolled back.
